# 迭代架构设计与功能规格文档拆解计划

> RabbitAITest · 复刻 MeterSphere v3.x 社区版功能面的一站式开源测试工作台
> 本文档回答三个问题：**文档体系怎么组织、82 份功能规格怎么拆、按什么顺序写**

---

## 一、总体方法论

### 执行原则

1. **对标基线唯一**：所有功能规格以 [../MeterSphere功能清单.md](../MeterSphere功能清单.md) 为唯一对标基线（该清单由官方文档 + 代码库逆向调研产出）。每份规格文档必须在「元信息表 · 对标基线」中注明对应清单章节；清单未覆盖的细节标注「超出基线，自主设计」。
2. **三层文档结构**：架构文档（全局约束）→ 迭代文档（sprint-overview）→ 功能规格（MODULE-NNN）。任何功能文档必须可回溯到架构决策，任何架构决策必须可前向追溯到至少一份功能规格。
3. **上游未稳不写下游**：依赖链（§五）不可颠倒。例如 `EXEC-002`（资源池调度）未确认前，不写 `API-008`（场景批量执行）。
4. **一次建齐数据模型**：核心域表（用例/接口/场景/执行/报告）在 Sprint 0 一次性建齐全部列（含未启用列），后续迭代只做「开关 + 种子 + 索引」，杜绝核心表反复 DDL（详见 `architecture/test-domain-model.md` §6）。
5. **每个 Sprint 一条可演示主线**：迭代概览必须定义一条浏览器可操作端到端路径作为验收主线，不接受「接口写完了 UI 还没有」的交付。
6. **高保真与人工确认门禁（硬性）**：每个功能点必须先产出高保真原型（`docs/design/{MODULE}-NNN-{slug}/`）并经人工确认，才能开始功能迭代开发；纯后端/引擎类规格（INFRA/EXEC/QA 等）以接口契约（OpenAPI/事件流 schema）评审替代。规范全文见仓库根 [AGENTS.md](../../AGENTS.md) §1 门禁 2。
7. **远程 CI 与 Sprint 交付纪律（硬性）**：以 GitHub Actions 远端 CI 结果为交付标准（本地自测通过不算完成）；main 保持绿；每个 Sprint 收尾必须 commit + push 到远程并确认远端 CI 全绿，同时完成状态流转与 changelog（AGENTS.md 门禁 9，流程见 rules/git-workflow.md §8）。

### 文档规模

| 层 | 数量 | 说明 |
| --- | --- | --- |
| 架构文档 | 9 份 | 全局约束，一次确定长期遵循 |
| 迭代概览 | 11 份 | 每个 Sprint 一份 sprint-overview.md |
| 功能规格 | 82 份 | P0×10 / P1×16 / P2×48 / P3×8 / P4×8（含跨级），每份 300-600 行 |
| 支撑文档 | 4 份 | README 索引、需求文档、glossary、本计划 |

- 功能规格：`{模块缩写}-{三位序号}-{kebab-case 标识}.md`，模块内序号全局递增、不复用
- 迭代目录：`sprint-{N}-{主题}/`，N 从 0 起

## 三、规格文档统一模板

每份功能规格固定七章结构（与 RabbitProjects 对齐，竞品对标章替换为 MeterSphere 基线核对章）：

```
# {功能名}
| 元信息表：文档编号 / 所属迭代 / 优先级 / 所属模块 / 文档状态 /
|          最后更新日期 / 上游依赖 / 下游消费 / 上游依据（需求文档§）/
|          对标基线（MeterSphere功能清单§）/ 关联架构文档 /
|          高保真确认（确认人/日期/原型链接；未确认=待确认）/ 工作量估算 |

## 1. 概述
   1.1 功能定位（为什么需要、在系统中的位置）
   1.2 范围边界表（本迭代 ✅ / 后续迭代 ❌ 及去向编号）
   1.3 前置依赖表（依赖文档 + 阻塞原因）
   1.4 对标基线核对（清单章节逐条对照：完全复刻 / 简化实现 / 超出基线）
## 2. 业务逻辑
   状态机 / 流程图（mermaid）/ 规则明细 / 边界与异常
## 3. UI/UX 设计
   页面结构 / 交互细节 / 空态与权限态 / 对话式用例走查
   ——界面类规格必须附 docs/design/ 高保真原型链接，人工确认后方可进入编码
## 4. 技术架构
   数据模型（Prisma schema 级）/ API 契约（方法·路径·请求·响应，zod 定义）/
   前端组件与状态 / 引擎侧（如涉及 EXEC）/ 权限点
## 5. 测试用例
   功能用例表（前置/步骤/预期，编号与测试文件一致）+
   JMeter 接口用例清单（四类场景×四项断言，映射 tests/api/{MODULE}-NNN-*.jmx）+
   Playwright UI 用例清单（每条含 UI 断言 + Console 断言 + 接口断言三类，映射 tests/e2e/）+
   性能与安全注意
## 6. 竞品深度对标
   MeterSphere 实现方式 ↔ 本项目实现方式对照表 + 差异化决策及理由
## 7. 里程碑与验收
   交付清单 / DoD（前置：高保真已人工确认）/ 演示脚本 / 回归范围
   ——Sprint 收尾：commit + push 远程，GitHub Actions 远端 CI 全绿（rules/git-workflow.md §8）
```

**元信息表硬性要求**：`上游依赖` 必须与 `dependency-graph.md` 一致；`工作量估算` 按后端/前端/联调分列（人日）。

## 四、竞品对标分析框架

本项目只有一个对标产品 MeterSphere，对标分析框架固定四维（全部基于已调研的清单与代码实证，不得臆造）：

| 维度 | 内容 | 用途 |
| --- | --- | --- |
| 功能面 | 功能清单逐条映射（清单§章节 → 本项目文档编号） | 保证 100% 覆盖，README 索引维护映射表 |
| 数据模型 | MeterSphere 六域实体（api/functional/plan/project/system/bug）→ 本项目 test-domain-model | 借鉴实体关系，不照抄表结构 |
| 交互范式 | 三页签（API/CASE/MOCK）、脑图三态、模块树+列表通用能力 | UI/UX 章节的对齐基线 |
| 技术差异 | JMeter 引擎 → 自研 Node.js 内核；Java pf4j → TS 插件包+进程隔离；Kafka → Redis（BullMQ + Stream） | 每份规格 §6 必须阐明替换决策 |

## 六、质量控制

### 每份文档的验收标准
1. 元信息表完整，依赖关系与 dependency-graph 一致
2. 范围边界表明确「不做什么」且指向后续编号
3. 数据模型符合 test-domain-model 的「一次建齐」原则（新列需说明为何不能 Sprint 0 建）
4. API 契约符合 api-conventions（路径、信封、错误码、分页）
5. §6 对标核对逐条引用功能清单章节，无「与 MeterSphere 一致」这类无出处的断言
6. 验收标准可现场执行（浏览器操作路径或 curl 命令）
7. **高保真门禁**：界面类规格附 `docs/design/` 原型链接并有人工确认记录（元信息「高保真确认」字段）；纯后端规格附契约确认记录（AGENTS.md 门禁 2）
8. **自动化测试映射**：§5 用例表与 `tests/api/*.jmx`、`tests/e2e/*.spec.ts` 编号一一对应；UI 用例三类断言（UI/Console/接口）齐备（rules/testing.md）

### 风险缓解
| 风险 | 缓解 |
| --- | --- |
| 引擎自研范围失控 | 引擎规格冻结「HTTP only」至 Sprint 2 结束；协议插件化延后到 PLUG-002 |
| 与 MeterSphere 兼容承诺过重 | 兼容承诺限定：用例 Excel/Xmind 模板、jmx 导入、Swagger3/OpenAPI；不做双向迁移 |
| 企业版功能提前渗透 | Code Review 检查：P0-P2 迭代出现 ENTP 前缀文件即拒绝 |
| 文档与实现漂移 | 每份规格「文档状态」字段跟踪：Draft→Approved→Implemented→Verified |
